## 2026-06-13 - Rate-Limiter Argument Order Bypass on Authentication Endpoints
**Vulnerability:** The `guardRate` utility was invoked on `/admin/login` and `/admin/login/2fa` with 4 arguments instead of 5 (`guardRate(c, "admin-login:" + ip, 5, 600)` instead of `guardRate(c, "admin-login", ip, 5, 600)`). This caused the limit parameter `max` to receive 600 instead of 5/8, and `windowSec` to be `undefined`, causing `resetAt` calculations to evaluate to `NaN` and completely breaking rate limiting against brute-force attacks on admin credentials and 2FA TOTP challenges.
**Learning:** Functions accepting primitive arguments with overlapping types (e.g. `(c, scope, id, max, windowSec)`) can easily be miscalled without strict typing or options objects, especially when other rate-limiting functions like `rateLimit(key, max, windowSec)` use different signatures.
**Prevention:** Pass structured parameters or ensure callers match the exact signature `guardRate(c, scope, id, max, windowSec)` when applying endpoint rate limits.
