## 2026-07-20 - [Admin Rate Limiter Bypass and IP Spoofing Fix]
**Vulnerability:** An argument mismatch when calling `guardRate` in the `/admin/login` and `/admin/login/2fa` endpoints caused the `windowSec` (duration) parameter to be passed as `undefined`. Consequently, this caused `rateLimit`'s calculation of the key expiration timestamp `resetAt` to resolve to `NaN`. Because comparison with `NaN` evaluates to `false`, the rate limiter bucket never reset, effectively allowing 600 brute-force attempts per connection rather than the intended 5/8 attempts per 600 seconds, and completely blocking subsequent requests indefinitely once exceeded. Additionally, the endpoints relied on raw `X-Forwarded-For` header parsing which allowed IP spoofing in Cloudflare environments.

**Learning:** Rate limit guards must be called with accurate positional arguments matching their definition. When a rate limit guard expects five arguments (context, scope, id, max, windowSec) but is mistakenly called with four arguments, typescript compilation may succeed due to loose parameter checks, but the omitted parameter will cause core logic failure (e.g. `NaN` timestamp math in redis/KV store rate limit logic). Furthermore, client IP resolution in Cloudflare environments must prioritize `cf-connecting-ip` to prevent trivial spoofing of `X-Forwarded-For`.

**Prevention:** Always define centralized helpers for IP extraction with defensive check (verifying `c?.req?.header` is a function), and ensure rate-limiting helper invocations strictly align with the `guardRate(c, scope, id, max, windowSec)` signature to preserve proper partitioning and window duration behavior.
